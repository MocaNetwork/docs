Choose a surface based on where your agent runs and how much of the experience you want to control. All of them use the same AIR Accounts and credentials.

## Choose a surface

| Surface | Fits | Your team provides | Availability |
| --- | --- | --- | --- |
| Agent APIs (REST) | A backend that binds agents to users and calls AIR directly | Backend services, secure key storage, the consent screen, and the user-facing flow | Documented endpoints for binding, agent sessions, credential listing and verification, and merchant checkout tokens. Contact the AIR team for environment access. See the [Agent API quickstart](/agentic-identity/partner-agent-api). |
| AIR Agent Plugin | An existing agent that needs callable AIR tools | Agent configuration and the surrounding user experience | Alpha, with sandbox-verified installation, account connection, and wallet, credential, and payment tools. |
| AIR Agent SDK | An application that needs programmatic control in code | The application interface and orchestration of its flows | Headless v0.1 developer kit, including `@mocanetwork/airkit-agent`. The hosted demo is a reference SDK application, not an installable Widget. |

## Start with identity

Start a commerce pilot with agent binding and credential verification:

1. Get the user's approval and bind the agent. See [Ask for consent before binding](/agentic-identity/delegation-and-consent#ask-for-consent-before-binding).
2. Run the receiving application's verification program for each request.
3. Share the result with the receiving application in a format it can check. See [What a verification result proves](/agentic-identity/how-it-works#what-a-verification-result-proves).

The Agent APIs return a verification result in a single call. The Plugin's tools cover program discovery, verification, and status polling, and can hand the user an issuer URL when they lack a credential.

A partner acting as a verifier sets up programs with AIR Kit's [verification](/airkit/usage/credential/verify). Issuing credentials is an issuer's job, with its own [backend integration](/airkit/usage/credential/issuing-credentials).

## Add checkout where the journey needs it

Identity tells the merchant whom the agent represents and which benefits apply. Checkout and payment need their own integration and authority.

For a supported merchant, an agent whose key includes `commerce.checkout` can mint a short-lived checkout token. The token's audience is the merchant, which verifies it during checkout. See [Create a checkout session](/api-reference/agents/create-checkout-session).

For wallet payments through the Plugin, decide where spending limits are enforced. Payment-tool caps don't cover direct wallet transfers. See [Spending limits](/agentic-identity/delegation-and-consent#spending-limits).

## Not yet available

Plan your integration without these:

- Delegation credentials, user-bound proof handoff, and delegated verification.
- Verify on Behalf, meaning verification without the user in session, which is at concept stage.
- Standing payment mandates.
- Onchain audit logs for every agent action.

For the Plugin and SDK, confirm package versions and tool names with the AIR team before you build. The [Agent APIs reference](/api-reference/agents/introduction) documents the REST endpoints.

Use [Partner fit](/agentic-identity/partners) to scope the first journey with the AIR team.
