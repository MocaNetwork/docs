AIR Identity provides the underlying identity and credential services. AIR Agent exposes tools and integration surfaces for an existing product. Choose the delivery surface based on how much control you need over the application and its interface.

<Note>
  Availability reflects product information reviewed on 27 September 2026. Plugin and SDK integrations have sandbox coverage. The Agent APIs are documented; confirm environment access with the AIR team. Confirm production access and supported versions for your integration. The Widget is planned.
</Note>

## Choose a delivery surface

| Surface | Fits | Your team provides | Availability |
| --- | --- | --- | --- |
| AIR Agent Plugin | An existing agent that needs callable AIR tools | Agent configuration and the surrounding user experience | Alpha tooling with sandbox-verified installation, account connection, and wallet, credential, and payment tools. |
| AIR Agent SDK | An application that needs programmatic control | The application interface and orchestration of its flows | Headless v0.1 developer kit, including `@mocanetwork/airkit-agent`; the hosted demo is a reference application. |
| Agent APIs (REST) | A backend that binds agents to users and calls AIR directly | Backend services, secure key storage, and the user-facing flow | Documented endpoints for binding, agent sessions, credential listing and verification, and merchant checkout tokens. See the [Agent API quickstart](/agentic-identity/partner-agent-api). |
| AIR Agent Widget | An application that wants an embedded approval interface | The host application and integration with its journey | Planned interface for approval and payment confirmation; an installable package is not yet available in this offering. |

The hosted demo demonstrates an SDK integration. It should not be treated as an installable Widget. With the Agent APIs, your backend binds the agent to the user's AIR Account while the user has an AIR Kit session.

## Start with identity

Start a commerce pilot with account binding and credential verification, which the [Agent APIs](/agentic-identity/partner-agent-api) support. The target end-to-end flow adds the appropriate delegation and user-bound proof handoff before the receiving application evaluates the request. Confirm those capabilities in the selected release before depending on them.

The Plugin's verification tools cover program discovery, verification, and status polling. The Agent APIs list the user's credentials and return a verification result in a single call. If the user lacks a credential, the agent can surface the issuer's URL. Read [How it works](/agentic-identity/how-it-works) for these roles and [AIR credential verification](/airkit/usage/credential/verify) for the underlying verification model.

A partner acting as a verifier can use AIR Kit's verification capabilities. Issuing credentials is an issuer responsibility, with its own [backend integration](/airkit/usage/credential/issuing-credentials).

## Add payments where the journey needs them

Identity determines who the agent represents and which benefits the user qualifies for. Checkout and payment still need their own integration and authority checks.

For a supported merchant, an agent whose key includes the `commerce.checkout` scope can mint a short-lived checkout token. The token's audience is the merchant, which verifies it during checkout. See [Create a checkout session](/api-reference/agents/create-checkout-session).

Confirm the supported payment route, the approvals it requires, and where limits are enforced. The documented payment-tool policy does not establish wallet-wide protection for direct transfers. See [Spending limits and enforcement](/agentic-identity/delegation-and-consent#spending-limits-and-enforcement).

## Confirm the implementation contract

Before writing against a specific release, confirm:

- Package names, versions, and the environment available to your team.
- Delegation credential format, supported scope fields, and presentation flow.
- Verification inputs and outputs for surfaces other than the Agent APIs, status checks, and request binding.
- Which flows require the user to be present and how additional approval works.
- Delegation revocation behavior, payment enforcement, and Plugin or SDK error handling.

Credential verification through the Agent APIs or Plugin is distinct from the target delegated-verification flow. Delegation credentials, user-bound proof handoff, and production revocation behavior remain release-dependent; Verify on Behalf remains at concept stage. The [Agent APIs reference](/api-reference/agents/introduction) covers endpoints and payloads for binding, sessions, credentials, and checkout. Release-specific guarantees for other surfaces belong in their versioned references. Standing payment mandates and chain-anchored audit logs for every action are also outside the current capabilities established by these docs.

Use [Partner fit](/agentic-identity/partners) to scope the first journey with the AIR team.
