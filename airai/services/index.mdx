AIR AI Services is the user-facing product line for operating agents with AIR-powered identity, money, consent, policy, and auditability. It defines what an agent can know, prove, share, collect, store, spend, authorize, hold, route, or settle on behalf of a user.

<Info>
**The trust equation.** Identity controls what an agent can know or prove. Money controls what an agent can spend or authorize. Policy sets the boundary. Audit proves what happened.
</Info>

## Why this layer exists

Agents are becoming a new interface for users to discover, decide, verify, book, buy, and transact. To do meaningful work, an agent needs to use two sensitive resources: **identity** (information about the user) and **money** (authority to spend, authorize, or settle value).

Without a clean permission layer, every agent integration ends up with too much access (creating data leakage and financial risk) or too little (making the agent useless).

AIR AI Services answers two linked questions:

1. **Identity question:** What can the agent know, prove, collect, store, or share?
2. **Money question:** What can the agent spend, authorize, hold, route, or settle?

## How each agent relationship uses these streams

The same identity data can sit in either stream depending on the agent relationship.

| Relationship | Stream 1 — data the agent gets | Stream 2 — data / proofs shared onward |
| --- | --- | --- |
| **Butler** (user-owned) | Rich, persistent context — preferences, addresses, loyalty, travel history, payment rules. | Field-level disclosure or proofs as needed for the booking, delivery, or service. |
| **Concierge** (merchant-owned) | Limited and service-specific — account, booking context, merchant history. | Eligibility proofs, age proofs, KYC status, payment authorization, delivery details. |
| **Platform** (platform-owned) | Platform routing context, session state, marketplace context. | Proof handoff, attestations, encrypted payloads, freshness, revocation status, payment authorization. |

For more on the three relationship types, see [Agent taxonomy](/airai/agent-taxonomy).

## What it means in practice

<AccordionGroup>
  <Accordion title="A travel agent gets loyalty status without seeing your full membership record">
    The agent uses AIR Agentic Identity to retrieve only the loyalty tier and preference claims it needs to rank options, with a freshness check. The credential issuer is never called by the agent directly.
  </Accordion>
  <Accordion title="A merchant verifies you're 18+ without learning your date of birth">
    AIR Agentic Identity issues a proof-only attestation. The merchant receives a verifiable claim and a compliance receipt; raw birth date never leaves AIR's identity boundary.
  </Accordion>
  <Accordion title="An agent can buy ETH but is blocked from betting on Polymarket">
    AIR Agentic Money + Policy enforce a spend mandate with category allowlists and merchant scope. The agent receives a payment authorization for allowed categories, and a denial receipt for blocked ones.
  </Accordion>
  <Accordion title="You revoke an agent's access at any time">
    AIR Policy + Audit produces a revocation event. Every existing permission, mandate, and proof reference is invalidated; subsequent agent calls return a revocation status instead of executing.
  </Accordion>
</AccordionGroup>

## Out of scope for this product line

- Building AI agents or agent wrappers
- Agent orchestration or multi-agent coordination
- Building new payment rails or commerce protocols
- Agent-to-agent autonomy as a primary surface — covered in a future phase once human-to-agent delegation and standards mature

Developer tooling, MCP packages, plugins, and embeddable authorization flows are covered by [AIR AI Studio](/airai/studio/index). Base SDK and enterprise integrations are covered by [AIR Kit](/airkit/index).
