This recipe shows how to verify a user's credential inside your application using the AIR Kit SDK. Verification is **program-driven**: a verification program in the Developer Dashboard defines which schema and issuers are accepted, what conditions are checked, and whether a zero-knowledge proof is required. Your code passes a Partner JWT and the program ID; the SDK handles credential discovery, consent, and proof generation.

## What you'll build

1. A verification program configured in the Dashboard.
2. A server endpoint that signs a Partner JWT with `scope: "verify"`.
3. SDK code that prompts the user to present a credential.
4. Application logic that reacts to the verification `status`.

## Prerequisites

- AIR Kit SDK installed and initialized. See [Install and initialize](/get-started/installation).
- [Partner JWT signing](/get-started/partner-authentication) configured, with your public key published through a registered [JWKS endpoint](/get-started/jwks-setup).
- At least one credential issued to a test user (see [Quickstart: Issue credentials](/get-started/quickstarts/issue-credentials)).

## Step 1: Create a verification program

1. Open the [Developer Dashboard](https://developers.sandbox.air3.com/dashboard).
2. Under **Verifier → Programs**, create a program and select the schema and issuers you accept.
3. Configure the conditions to check (for example, `tier == "Gold"` or `age > 18`), the proof requirement, and off-chain or on-chain mode.
4. Publish the program and copy its **verification program ID**.

## Step 2: Sign a Partner JWT on your server

The SDK call requires a short-lived Partner JWT with `scope: "verify"`. Sign it on the server; never ship the private key to the browser.

```js
const jwt = require("jsonwebtoken");
const fs = require("fs");

const privateKey = fs.readFileSync("path/to/private.key");

function getVerifyToken() {
  const now = Math.floor(Date.now() / 1000);
  return jwt.sign(
    { partnerId: process.env.PARTNER_ID, scope: "verify", iat: now, exp: now + 5 * 60 },
    privateKey,
    { algorithm: "RS256", header: { kid: process.env.KEY_ID, typ: "JWT" } }
  );
}

// Express example — apply your own session checks first
app.post("/api/verification-token", requireAuth, (req, res) => {
  res.json({ token: getVerifyToken() });
});
```

The `kid` must match a key in your registered JWKS. See [Partner Authentication](/get-started/partner-authentication) for ES256 and other language examples.

## Step 3: Initialize AIR Kit and log the user in

```ts
import { AirService, BUILD_ENV } from "@mocanetwork/airkit";

const airService = new AirService({ partnerId: process.env.NEXT_PUBLIC_PARTNER_ID });
await airService.init({ buildEnv: BUILD_ENV.SANDBOX }); // or BUILD_ENV.PRODUCTION

if (!airService.isLoggedIn) {
  await airService.login();
}
```

## Step 4: Request credential verification

Fetch the token from your server and call `verifyCredential` with the program ID.

<Tabs>
<Tab title="Web">

```ts
async function verifyLoyaltyTier() {
  // Your server returns a Partner JWT and a one-time nonce
  const response = await fetch("/api/verification-token", { method: "POST" });
  const { token, nonce } = await response.json();

  const result = await airService.verifyCredential({
    authToken: token,
    programId: process.env.NEXT_PUBLIC_VERIFY_PROGRAM_ID,
    fieldsToDisclose: ["tier"],
    nonce,
  });

  if (result.status === "Compliant") {
    grantAccess(result.verifiablePresentation);
  } else {
    denyAccess(result.status);
  }
}
```

</Tab>

The SDK opens its built-in UI, finds matching credentials on the holder's device, asks the user to consent, and generates the presentation. The verifier receives the outcome and the disclosed claims defined by the program, not the raw credential data.

If the user may not hold the credential yet, pass an optional `redirectUrl` pointing to the issuer's claim page.

## Step 5: Gate features based on the status

`verifyCredential` resolves to a result discriminated on `status`. Only `"Compliant"` carries a `verifiablePresentation`; every other status (such as `"Non-Compliant"`, `"NotFound"`, `"Expired"`, or `"Revoked"`) has no presentation. See the [response reference](/products/identity/verify#response) for the full list.

```ts
async function grantAccess(presentation) {
  // Verify the SD-JWT on your backend before unlocking the feature.
  const check = await fetch("/api/verify-presentation", {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ verifiablePresentation: presentation }),
  });
  if (check.ok) unlockFeature();
}

function denyAccess(status) {
  if (status === "Non-Compliant") {
    // Credential exists but fails the program's conditions — show a restricted view.
    return;
  }
  // Missing, pending, expired, or revoked credential — send the user to the
  // issuer flow or ask them to renew. Log `status` to distinguish the cases.
}
```

Wrap the call in `try/catch`: a cancelled consent dialog or a rejected token rejects the promise rather than returning a status.

<Warning>
A `"Compliant"` result is checked in the user's browser, and the presentation wrapper is not signed. Before granting anything of value, verify the SD-JWT inside it on your backend, including the key-binding JWT against your nonce. See [Verify SD-JWT on your backend](/products/identity/verify-sd-jwt).
</Warning>
