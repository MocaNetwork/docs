This guide adds credential verification to your web app. Your verification
program defines the accepted credentials and requested claims. AIR Kit handles
credential discovery, the consent screen, and presentation generation. Your
backend issues a nonce and verifies the returned SD-JWT presentation.

## Before you start

You need:

- An AIR Developer Dashboard account and Partner ID, with verifier functionality enabled
- A web app served over HTTPS, with its origin whitelisted under **Account → Domains**
- A public HTTPS JWKS endpoint registered for your Partner ID
- A server endpoint that signs short-lived Partner JWTs with `scope: "verify"`
- A test holder with a matching credential from an issuer accepted by your program,
  or access to that issuer's claim flow
- A supported Node.js version for your web framework and AIR Kit

You do not need to operate an issuer backend or database to verify another
issuer's credentials. The [issuance quickstart](/get-started/quickstarts/issue-credentials)
is optional. AIR login is required for this SDK flow; the code below includes it.

## Step 1: Configure a verification program

1. Open the [Sandbox Developer Dashboard](https://developers.sandbox.air3.com/dashboard)
   and copy your Partner ID from **Account → General Settings**.
2. Under **Verifier → Programs**, create a program and select the accepted schema
   and issuer configuration.
3. Select `SD_JWT_VC` as the accepted proof type and choose the claims to request.
4. Publish or apply the program so it is active, and copy its verification program ID.

Predicate checks such as "age greater than 18" without revealing the value, and
on-chain verification, need Iden3 credentials. See
[Iden3 credentials](/products/identity/iden3-credentials).

## Step 2: Configure Partner authentication

The code below uses a Next.js app. Keep the private key on the server, including
during local development.

```bash
npm i @mocanetwork/airkit jose @sd-jwt/sd-jwt-vc
```

Set your app's environment variables:

```bash
# Browser-safe
NEXT_PUBLIC_PARTNER_ID=<dashboard-partner-id>
NEXT_PUBLIC_VERIFY_PROGRAM_ID=<verification-program-id>

# Server-only
PARTNER_PRIVATE_KEY=<pkcs8-private-key-body-without-pem-markers>
PARTNER_PUBLIC_KEY=<public-key-body-without-pem-markers>
SIGNING_ALGORITHM=RS256 # or ES256

# Server-only: what your backend accepts
AIR_TRUSTED_ISSUERS=<did:web:issuer-host>
AIR_EXPECTED_VCT=<credential type (vct)>
```

Verification fails until AIR can fetch your JWKS. If you haven't set one up for
this Partner ID, follow [JWKS endpoint](/get-started/authentication/jwks-endpoint). If you already
issue credentials with the same Partner ID, reuse that JWKS and key pair.

Your backend must know which user it issues a nonce to, so it can check that
user's nonce when the presentation comes back. The browser sends the user's AIR
login token as `Authorization: Bearer <token>`, and the backend validates it
against AIR's JWKS (see [Sessions](/get-started/authentication/sessions)).
This file does that, and stores one pending nonce per user:

```ts lib/air-session.ts
import { createRemoteJWKSet, jwtVerify } from "jose";

// Sandbox AIR login keys, tried in order. Production uses only
// https://static.air3.com/.well-known/jwks.json.
const AIR_JWKS = [
  "https://static.sandbox.air3.com/.well-known/jwks.json",
  "https://account.sandbox-testnet.air3.com/.well-known/jwks.json",
  "https://static.air3.com/.well-known/jwks.json",
].map((url) => createRemoteJWKSet(new URL(url)));

// Returns the AIR user ID (`sub`) from a valid AIR login token, or null.
export async function getAirUserId(request: Request): Promise<string | null> {
  const header = request.headers.get("authorization") ?? "";
  const token = /^Bearer\s+(\S+)$/i.exec(header)?.[1];
  if (!token) return null;
  for (const keys of AIR_JWKS) {
    try {
      const { payload } = await jwtVerify(token, keys);
      if (payload.partnerId !== process.env.NEXT_PUBLIC_PARTNER_ID) return null;
      return typeof payload.sub === "string" && payload.sub ? payload.sub : null;
    } catch (error) {
      if ((error as { code?: string }).code === "ERR_JWKS_NO_MATCHING_KEY") continue;
      return null;
    }
  }
  return null;
}

// One pending nonce per user, valid for 5 minutes. This in-memory map serves a
// single server process; use your session store or database otherwise.
type Pending = Map<string, { nonce: string; expires: number }>;
const pending: Pending = ((globalThis as { airNonces?: Pending }).airNonces ??= new Map());

export function saveNonce(userId: string, nonce: string) {
  pending.set(userId, { nonce, expires: Date.now() + 5 * 60_000 });
}

// Returns the user's pending nonce and deletes it, so it is checked only once.
export function takeNonce(userId: string): string | null {
  const entry = pending.get(userId);
  pending.delete(userId);
  return entry && entry.expires > Date.now() ? entry.nonce : null;
}
```

Create a server endpoint for verification tokens:

```ts app/api/verification-token/route.ts
import { randomBytes } from "node:crypto";
import { NextResponse } from "next/server";
import { importPKCS8, SignJWT } from "jose";
import { getAirUserId, saveNonce } from "@/lib/air-session";

export async function POST(request: Request) {
  const userId = await getAirUserId(request);
  if (!userId) {
    return NextResponse.json({ error: "Authentication required" }, { status: 401 });
  }

  const partnerId = process.env.NEXT_PUBLIC_PARTNER_ID;
  const privateKeyBody = process.env.PARTNER_PRIVATE_KEY;

  if (!partnerId || !privateKeyBody) {
    return NextResponse.json(
      { error: "Missing Partner JWT configuration" },
      { status: 500 },
    );
  }

  try {
    const pem = privateKeyBody.includes("BEGIN PRIVATE KEY")
      ? privateKeyBody
      : `-----BEGIN PRIVATE KEY-----\n${privateKeyBody.trim()}\n-----END PRIVATE KEY-----`;
    const alg = process.env.SIGNING_ALGORITHM ?? "RS256";
    const key = await importPKCS8(pem, alg);
    const token = await new SignJWT({ partnerId, scope: "verify" })
      .setProtectedHeader({ alg, kid: partnerId, typ: "JWT" })
      .setIssuedAt()
      .setExpirationTime("5m")
      .sign(key);

    // One-time nonce for the key-binding JWT, stored for this user.
    // /api/verify-presentation checks it and deletes it.
    const nonce = randomBytes(16).toString("base64url");
    saveNonce(userId, nonce);

    return NextResponse.json({ token, nonce });
  } catch {
    return NextResponse.json(
      { error: "Unable to sign verification token" },
      { status: 500 },
    );
  }
}
```

This example uses your Partner ID as the JWKS key's `kid`. If your registered
key uses a different `kid`, use that value in the token header.

## Step 3: Initialize AIR Kit and start verification

Call this helper from a browser event handler, such as your **Verify** button:

```ts lib/verify-credential.ts
import { AirService, BUILD_ENV } from "@mocanetwork/airkit";

let servicePromise: Promise<AirService> | undefined;

function getAirService(): Promise<AirService> {
  servicePromise ??= (async () => {
    const partnerId = process.env.NEXT_PUBLIC_PARTNER_ID;
    if (!partnerId) throw new Error("Partner ID is required");

    const service = new AirService({ partnerId });
    await service.init({ buildEnv: BUILD_ENV.SANDBOX });
    return service;
  })().catch((error) => {
    servicePromise = undefined;
    throw error;
  });
  return servicePromise;
}

export async function verifyCredential() {
  const programId = process.env.NEXT_PUBLIC_VERIFY_PROGRAM_ID;
  if (!programId) throw new Error("Verification program ID is required");

  const service = await getAirService();
  if (!service.isLoggedIn) await service.login();

  // Your server returns a Partner JWT and a fresh nonce stored for this user.
  // The AIR login token tells it who the user is.
  const response = await fetch("/api/verification-token", {
    method: "POST",
    headers: {
      "content-type": "application/json",
      authorization: `Bearer ${(await service.getAccessToken()).token}`,
    },
  });
  const body = (await response.json()) as {
    token?: string;
    nonce?: string;
    error?: string;
  };
  if (!response.ok || !body.token || !body.nonce) {
    throw new Error(body.error ?? "Unable to obtain verification token");
  }

  const result = await service.verifyCredential({
    authToken: body.token,
    programId,
    fieldsToDisclose: ["historical_amount"], // or "*" for every field
    nonce: body.nonce,
  });
  if (result.status !== "Compliant") return { status: result.status, verified: false };

  // AIR's check ran in this browser. Only your backend's answer counts.
  const check = await fetch("/api/verify-presentation", {
    method: "POST",
    headers: {
      "content-type": "application/json",
      // Fetch the token again: the consent screen may have taken time
      authorization: `Bearer ${(await service.getAccessToken()).token}`,
    },
    body: JSON.stringify({ verifiablePresentation: result.verifiablePresentation }),
  });
  const verdict = (await check.json().catch(() => null)) as {
    verified?: boolean;
    claims?: Record<string, unknown>;
  } | null;
  return {
    status: result.status,
    verified: check.ok && verdict?.verified === true,
    claims: verdict?.claims,
  };
}
```

The nonce needs at least 128 bits of randomness, as in the token route above. If your flow needs to redirect users to an issuer when they lack
a credential, add the optional `redirectUrl` pointing to that issuer's claim page.

## Step 4: Obtain consent and handle the result

During verification, AIR Kit:

1. Finds matching credentials. If none exist, the user needs to complete an
   accepted issuer's issuance flow before verification can succeed.
2. Fetches and decrypts the credential on the holder's device.
3. Shows the requested data and asks the user to consent.
4. Records consent and generates the presentation. Because you passed a
   nonce, the holder signs a key-binding JWT with their private signing key.
   It covers the credential, the disclosed claims, nonce, and
   `programId`, so a leaked presentation cannot be replayed.
5. Returns the outcome to your app.

Handle both returned statuses and errors, including a cancelled flow. Grant
access only after a successful result appropriate to your application's trust
requirements.

```ts
import { verifyCredential } from "@/lib/verify-credential";

try {
  const { status, verified, claims } = await verifyCredential();
  if (verified) {
    // Your backend verified the presentation: act on `claims`
  } else {
    console.log("Verification did not pass:", status);
  }
} catch {
  console.log("Verification was cancelled or could not complete. Allow a retry.");
}
```

## Step 5: Verify the presentation on your backend

The `Compliant` check runs in the browser, and the presentation wrapper is not
signed. Your backend verifies the SD-JWT inside it: issuer signature,
disclosures, expiry, credential type, and the key-binding JWT against the
user's nonce and your `programId`.

[Verify SD-JWT on your backend](/products/identity/verify-sd-jwt) as
`lib/verify-air-sd-jwt.ts`, then create the route:

```ts app/api/verify-presentation/route.ts
import { NextResponse } from "next/server";
import { getAirUserId, takeNonce } from "@/lib/air-session";
import { verifyAirSdJwt } from "@/lib/verify-air-sd-jwt";

export async function POST(request: Request) {
  const userId = await getAirUserId(request);
  if (!userId) {
    return NextResponse.json({ error: "Authentication required" }, { status: 401 });
  }

  // Take the nonce before verifying: it is single-use even if verification fails
  const expectedNonce = takeNonce(userId);
  if (!expectedNonce) {
    return NextResponse.json({ error: "No pending verification" }, { status: 400 });
  }

  const body = await request.json().catch(() => null);
  try {
    const { claims } = await verifyAirSdJwt({
      verifiablePresentation: body?.verifiablePresentation ?? {},
      programId: process.env.NEXT_PUBLIC_VERIFY_PROGRAM_ID!,
      expectedNonce,
      requireHolderBinding: true,
      trustedIssuers: (process.env.AIR_TRUSTED_ISSUERS ?? "")
        .split(",")
        .map((iss) => ({ iss: iss.trim() as `did:web:${string}` })),
      expectedVct: process.env.AIR_EXPECTED_VCT!,
      requiredClaims: ["historical_amount"], // your fieldsToDisclose
    });
    // Grant access or record the result here, based on the verified claims
    return NextResponse.json({ verified: true, claims: { historical_amount: claims.historical_amount } });
  } catch {
    return NextResponse.json({ verified: false }, { status: 422 });
  }
}
```

## Step 6: Test the integration

Run the test through your [HTTPS tunnel](/get-started/authentication/jwks-endpoint#local-development-https-tunnel) URL, with the tunnel domain whitelisted under **Account → Domains** and the tunnel's JWKS URL registered.

Test with a matching credential, a credential that fails the requested condition,
and a user who declines consent. Confirm your app handles missing credentials,
expired tokens, and failed requests without granting access.

Also confirm your backend rejects a replayed presentation (a second submit gets
`400 No pending verification`), a presentation made for another `programId`, and
a presentation with a disclosure removed.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Partner JWT rejected | Public JWKS URL, matching `kid` and key pair, `scope: "verify"`, and token expiry |
| No matching credential | Program schema and accepted issuers, holder's credentials, and issuer claim flow |
| Backend rejects with `Key Binding JWT not exist` | The credential has a holder key but the KB-JWT is missing. Check you passed `nonce` |
| `400 { error: "No pending verification" }` | No stored nonce for this user: the presentation was already submitted (a replay), the nonce expired after 5 minutes, or the server restarted or another instance issued it |
| Backend rejects with `Invalid Nonce` | The KB-JWT nonce differs from the user's stored nonce, for example a presentation from an earlier attempt after a new token request replaced the nonce |
| Program unavailable | Correct environment, active program, and enabled verifier functionality |
